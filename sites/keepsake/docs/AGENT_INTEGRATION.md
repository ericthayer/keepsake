# Keepsake agent integration

## Status

The hosted remote MCP endpoint is `/mcp`. Browser-native WebMCP is implemented in `lib/webmcp.ts` and `app/components/agent/webmcp-bridge.tsx` but deliberately unmounted. It must pass registration, invocation, read-back, and invalid-input checks in a permitted browser with `document.modelContext` before activation. The normal website and remote server do not depend on browser WebMCP.

## Connect

For ChatGPT and Codex, use the private Keepsake plugin generated by Sites after publication. Install or connect it under **Plugins → Personal → Created by you**. No separate custom App or local MCP registration is required for that connection.

External agents or gateways use the authenticated Streamable HTTP endpoint:

```
https://keepsake-family-locker.ethayer-design.chatgpt.site/mcp
```

Sites owns OAuth, sign-in, and site access. Follow the authentication discovery/challenge returned by the platform using an OAuth-capable client. Do not put passwords, browser cookies, bypass tokens, or financial credentials in a gateway configuration. The server additionally requires the platform-provided signed-in user identity for every data tool; a service access credential alone cannot select a user's locker. Each site-scoped user sees their own locker. Sharing a site or saving a contact does not make that person the owner of somebody else's records.

## Protocol

- Stateless JSON-RPC over HTTP POST, with JSON responses.
- MCP `2026-07-28`: `server/discover`, `tools/list`, `tools/call`; complete results, version metadata, cache hints, and matching routing headers.
- Initialization compatibility for `2025-11-25`, `2025-06-18`, and `2025-03-26` clients; no session ID or SSE stream is required.
- `GET /mcp` returns 405. Batch requests are rejected. Notifications do not execute tools.
- Modern requests require matching `MCP-Protocol-Version`, `Mcp-Method`, and, for tool calls, `Mcp-Name`; the protocol version is also required in `params._meta`.
- Tool lists are deterministic. Data results are private and not cached by intermediaries.

Example discovery body (send through an authenticated MCP client):

```json
{
  "jsonrpc": "2.0",
  "id": "discover-1",
  "method": "server/discover",
  "params": {
    "_meta": {
      "io.modelcontextprotocol/protocolVersion": "2026-07-28",
      "io.modelcontextprotocol/clientCapabilities": {},
      "io.modelcontextprotocol/clientInfo": { "name": "my-gateway", "version": "1.0" }
    }
  }
}
```

## Tools

| Tool | Behavior |
| --- | --- |
| `keepsake_get_overview` | Counts, readiness, current version, and review date. |
| `keepsake_search_records` | Search accounts/documents by text, category, kind, or status, with pagination. |
| `keepsake_get_record` | Read one owner-scoped account or document record. |
| `keepsake_list_contacts` | Read and search contacts; no messaging or invitations. |
| `keepsake_get_family_guide` | Read the family note, contacts, and account/document directory. |
| `keepsake_prepare_change` | Store a validated before/after preview tied to the current version. |
| `keepsake_get_change` | Read an owner-scoped preview and its pending/applied/expired/conflict state. |
| `keepsake_apply_change` | Apply a preview after explicit user approval; requires `userConfirmed: true`. |

## Change flow

1. Read a tool result to get the current `version`.
2. Call `keepsake_prepare_change` with `expectedVersion` and one `change`.
3. Present the returned `preview.before` and `preview.after` to the user. The returned `reviewUrl` also opens the same comparison in the site.
4. After the user explicitly approves that exact change, call `keepsake_apply_change` with its `proposalId` and `userConfirmed: true`, or let the user apply it through the site's review dialog.
5. Read back the affected record or overview.

`userConfirmed` is an assertion made by the calling client. The server does not independently prove that a human saw a gateway's approval prompt. Configure your agent/gateway to require user approval for the apply tool. The website's **Apply this change** button provides direct user review in the UI.

Supported changes: create/update/delete a record; create/update/delete a contact; replace the family note; mark the locker reviewed. Record creation requires a title and category, with optional `kind: "account" | "document"`. Other record fields use the same UI schema. Contact creation requires a name. Partial updates must contain at least one field.

```json
{
  "expectedVersion": 0,
  "change": {
    "action": "create_record",
    "record": {
      "title": "Primary checking account",
      "category": "banking",
      "organization": "My bank",
      "website": "https://example.com/login",
      "reference": "1234",
      "location": "Family records folder",
      "status": "review"
    }
  }
}
```

Previews expire after 15 minutes. At most 20 recent proposals are retained per user during that period. Expired proposals are pruned lazily when the user prepares another change. Applied proposals are retained until expiration so retries can return their original receipt. The locker update and proposal receipt are one D1 transaction. Any UI or agent write invalidates an older unapplied preview, including a write with identical values. There is no background release, financial-account access, invitation, account linking, or beneficiary permission change.

The open site checks for remote changes every 15 seconds while visible and on focus. It does not refresh over an open editing or review dialog; stale saves fail with a version conflict.

## Verification

Run `npm run test:agents` for real SQLite migration/transaction tests, tool workflows, owner isolation, confirmation validation, unsafe input, expiration, stale-write handling, rollback, and modern/legacy RPC behavior. Run TypeScript and the Sites build helper before publication.

No live browser WebMCP verification has been performed in this environment. To enable it after QA, mount the exported `WebMcpBridge` with the locker's navigation and refresh handlers; do not change the approved design scaffold.
